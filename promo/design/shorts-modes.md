### 冒頭の作り方

1. **場面を探す**: 撮影ログ(`capture/raw/long-*/events.json`)から、`collapse`(まとめて崩れる)・`parry`(打ち返し)・`BlastExploded`(爆発)・`BlockFell` が密な 2.5〜3 秒を探す。出来事の時刻は `video_s`(録画の先頭からの秒)。候補はコマを並べた画像にして、ボール・パドル・崩れる所が枠から外れないかを目で確かめる。
2. **大きく映す**: ゲーム画面の枠を、ほかの場面(縦 406px)より大きくする。v014 は枠 880×608、映像 862×590、表示範囲(crop)は x=440, y=40, 1520×1040(盤面の左右の壁と上の HUD の一部を切る)。寄せすぎると、パドルやボールが枠の外に出る(e002 で出た)。
3. **音を上げる**: ゲーム映像のレイヤーの `volume` で、冒頭だけゲームの音を上げる(省略時は 0.52。v014 は 3.0)。上げる前に、その区間の最大音量を測る(`ffmpeg -ss <開始> -t 3 -i <録画> -af volumedetect -f null -`)。v014 の録画は最大 -10dB だったので、3 倍で崩れる瞬間が声と同じくらいになる。
4. **文字**: 見出し・吹き出しは、使える画像が `assets/text/` にあれば使う(v014 は `shorts-play/mitsuba_headline_3.png`・`mitsuba_v05_bubble_3.png`)。なければ「文字の画像の作り方」(`shorts-play.md`)で作る。
5. **確かめる**: `check_layout.py`、0 秒目のコマ(黒くないか)、冒頭 3 秒を 0.25 秒ごとに並べたコマ、場面ごとの音量(`ebur128`)。聞こえ方は本人に確かめてもらう。

### 投稿のとき

- 送る前に `records/videos.csv` に行を足す(投稿日は空のまま。送ると道具が書き込む)。

## 型を変える実験(2026-11-23、本人が決定)

**基本の型はワカナのショートまで。そのあとは、中身だけを変えて比べる。** 公開時刻(19:30)と、通常尺と組で出すこと(30 分前に通常尺)はそのまま。

### 決めた理由(11/20 までの数字)

| 型 | 動画 | 1 日目の再生 | 平均視聴率 | 半分の時点の維持 |
|---|---|---|---|---|
| 1 つの面白さに絞るキャラクター動画(21:00) | v009「この弾、返せる?」 | 1,154 | 52% | 0.43 |
| | v010「あっ、落ちた…からのクリア!」 | 1,033 | 49% | 0.39 |
| | v011「猶予は0.1秒。」 | 935 | 54% | 0.48 |
| 基本の型(4 モードの案内、19:30) | v014 ミツバ | 115 | 38% | 0.25 |
| | v015 アカネ | 144 | 45% | 0.31 |

- どの動画も、再生の 9 割以上が公開 1 日目。最初に試しに見せた人の反応で決まっている。
- 新しく入れた人(App Store の初回ダウンロード)は、ふだん 1 日 0〜1 件。11/14 だけ 4 件(ほかに入れ直し 2 件)で、11/10〜20 の 10 件中 4 件がこの日。前日 11/13 21:00 に v009 を公開していた。ダウンロード合計の山(11/14 の 20 件、11/17 の 14 件)は、大半がリリース後の自動アップデート。
- 通常尺(l001・l005)は 2〜3 回。ショートの「関連動画」から人はほぼ流れていない。

### 1 本目: v009 をもとに、焼き直しにしない

本人の方針は「同じ内容では前回の数字どまり」。ショートについて調べたことと、Codex の astra(gpt-6-astra)の案(2026-11-23)。

調べたこと(制作会社などのブログが多く、YouTube の公式の数字ではない):
- ゲームのショートは、遊べる面白さを 1 つ、ひと目でわかるように見せる。説明を並べない。
- 冒頭は派手な結果よりも、続きが気になる未解決の場面(弾が迫る、崩れる直前)。ゲームの広告では「ギリギリ」「失敗しそう」が効くという報告がある。
- ゲーム名は早めに出す。ほとんどの人はリンクを押さず、ストアで名前を検索する。ショートの説明欄の URL は押せない(YouTube の公式ヘルプ)。
- 広告っぽい呼びかけは避け、動画の中で答えられる問い(「早かった?ぴったり?」)でコメントを呼ぶ。
- 終わりを冒頭につなげて、見直す理由を作る(ループ)。
- 本数を多く出すと効く例がある(『Hamster Hunter』は 1 日 3〜4 本、1 本あたり 3 万〜10 万回)。

astra の 3 案(24 秒、ゲーム画面が主役。18〜22 秒に「PARRY BREAK|無料|iOS / Android」と検索の案内):
1. **「押すのは、まだ。あなたならいつ?」**(astra のおすすめ): 迫る弾を見せて、視聴者に心の中でタイミングを当ててもらう → 3 秒で答え「ここっ!」 → 崩れる → 目印なしでもう 1 問 → 「早かった?ぴったり?コメントで教えて」 → 冒頭につながる終わり。
2. **「白い 1 個が消えたら、どこまで落ちる?」**: 崩れ方を予想させる二択。崩れ方がひと目でわかる盤面の録画が要る。
3. **「さっきまで怖かった弾が、全部貫通する」**: 迫る弾 → 打ち返す → FEVER → 崩れる、の小さな物語。24 秒には情報が多め。

**1 本目は案 1「タイミング問題」**(2026-11-24 本人が決定)。

### 今後のショートの構成(たたき台、2026-11-24)

「案内」ではなく、見ている人が頭の中で 1 回遊べる作りにする。キャラは案内役ではなく、一緒に見て驚く人(台詞は 10 文字前後の短い反応)。

| 秒 | やること |
|---|---|
| 0〜1 | 決着のついていない場面と大きな問い。ゲーム名は小さく最初から |
| 1〜3 | 答えを効果音つきで |
| 3〜10 | ごほうび(崩れる、FEVER) |
| 10〜16 | 2 問目(少し難しく) |
| 16〜19 | 答えと、コメントへの問いかけ |
| 19〜22 | プレイの上に「無料・PARRY BREAK で検索」 |
| 22〜24 | 冒頭の場面につなげる(ループ) |

回ごとに遊びを 1 つ変えて比べる候補: タイミング問題 → 崩れ方の予想 → 逆転(v010 の型)→ 数字の挑戦(v011 の型)。勝った遊びをシリーズにし、5 人が交代で出題する。場面は `events.json` と `longform/scene_proposals.py` で探す(例: 弾が迫ってから JUST まで 2 秒以内)。

### 比べる数字

同じ経過時間(24 時間・72 時間・7 日)で、v014・v015・ワカナの分と比べる。
- Studio の「視聴 vs スワイプ」(冒頭でスワイプされずに見られた割合)
- 3 秒・12 秒の維持率、平均視聴率(目安は 65% 以上、12 秒の維持 55% 以上。v009 は 52%・43%)
- 公開の翌日〜翌々日の初回ダウンロード(ふだんの 0〜1 件と比べる。ほかの告知も記録する)

## 撮影(1.5.0)

スマホにはストア版(Google Play の 1.5.0 以前)が入っていて、手元の鍵で署名した APK は上書きできない(消すとセーブデータが消える)。そこで dev の作業フォルダで次の 3 点だけ変えてビルドし、別アプリ `com.watsuwo.parrybreak.promo` として並べて入れた(リポジトリには入れていない)。

1. `android/app/build.gradle.kts` に `applicationIdSuffix = ".promo"`
2. `lib/services/ads.dart` の `enabled` を、撮影用ビルドでは false(正式な広告枠にリクエストしないため)
3. `pubspec.yaml` の Flutter の版の指定を `">=3.47.6 <3.48.0"`(この PC は 3.47.9)

ビルドの引数は JUST 狙い版(promo/README.md)。APK は `promo/capture/apk/promo_just_v1.5.0_side.apk`(git 外)。撮影は `promo/capture/capture_mode.sh <title|endless|daily|practice|stage> <テイク>`。エンドレスは 120 秒で R6 前後まで進み、ボスの R10 には届かない。
