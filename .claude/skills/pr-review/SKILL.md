# PR のレビュー

`dev` 向けの PR は、このレビューで `needs-fix` が付かず、CI(チェックとエミュレーターでのスモークテスト)が通り、人が Approve するとマージされる(`.github/workflows/pr.yml`・`merge.yml`、運用は `docs/release-flow.md`)。人は **このレビューの所見と PR の本文を頼りに** Approve するかを決めるので、コードを細かく読まない。ここでの見落としはそのまま次のリリースに入る。逆に、好みの指摘で止めるとリリースが遅れる。**見るのは「出すと困るもの」だけ** にする。

## 1. 変更を集める

```sh
gh pr view <番号> --json number,title,body,baseRefName,headRefName,labels,files
gh pr diff <番号>
```

- 差分だけで判断しない。変更した関数の呼び出し元・テスト・関連する JSON は、チェックアウトしたファイルを読んで確かめる(CI ではチェックアウトが PR の内容になっている)。
- `flutter analyze` / `flutter test` は `check.yml` が、スモークテスト(`integration_test/smoke_test.dart`)は `pr.yml` の `e2e` が別に動かすので、ここでは実行しない。テストが **足りないか** だけを見る。
- `app/lib/l10n/app_localizations*.dart` は生成物なので、中身は読まずに `.arb` と合っているかだけを見る。

## 2. 観点

変更したファイルに当てはまる節だけを見る。各項目の「→」の先が、指摘の目安。

### 2.1 コア(`app/lib/core/`)

コアは純粋な Dart で、60Hz 固定・決定的に動く(`docs/native-app-spec.md` 5.1)。

- `package:flutter` や `dart:ui` を import している → 不具合(コアの原則に反し、単体テストで動かせなくなる)
- `dart:math` の `Random()`、`DateTime.now()`、`Stopwatch`、実時間の `Duration` を使っている → 不具合。乱数は `sim/rng.dart` の `Mulberry32` をシードから作る。時間はステップ数(1/60 秒)で数える
- `Mulberry32` や `procedural_generator.dart` を変えた、または乱数を引く順番・回数が変わった → 同じウェーブの配置が変わる。`test/core/layout_parity_test.dart`(`golden/layouts.json`)が通るかを CI で確かめる。意図した変更なら、PR の本文に理由があるか
- 判定の窓(パリィの ±12 / 30 / 100ms)、スコアの倍率、降下速度などの数値をコードに直書きしている → `config/tuning.dart` の Tuning に置く(ステージごとの上書きが効かなくなる)
- 描画・音・振動を直接呼んでいる → `GameEvent` を発行して購読側で処理する
- 浮動小数の比較・境界(`<` と `<=`)、1 フレームの取りこぼし、リストを回しながら消す、を変更した箇所で疑う

### 2.2 保存データ(`app/lib/services/records.dart`・`settings.dart`・`ads.dart`)

上書きインストールで記録と設定が残ることは、実機確認の項目(`docs/release-flow.md` 第8章)。壊れると取り返せない。

- `SharedPreferences` のキー(`records`、`settings.v1`、`ads.*`)を変えた、または消した → 不具合(前の記録が読めなくなる)。変えるなら古いキーを読んで移す処理が要る
- `toJson` のフィールド名・型を変えた → 古い JSON を `fromJson` で読めるか。足したフィールドは欠けていても既定値で読めるか
- `Records.version` を上げた → 前のバージョンからの移行と、そのテストがあるか。互換をなくすならメジャーバージョン(`release-flow.md` 第1章)
- 記録はステージの `id` をキーに、星は `stars` の **並び順** で持っている → 次の 2.3 も見る

### 2.3 ステージの JSON(`app/assets/stages/*.json`)

- 既存のステージの `id` を変えた、または消した → 不具合(そのステージの記録・星が消え、解禁がずれる)
- 既存のステージの `stars` を並べ替えた・途中に足した → 不具合(保存済みの星が別の条件のものになる)。足すなら末尾に
- `clear.type` / `stars[].type` が `native-app-spec.md` 5.5 の一覧にない、`rows` の幅や文字がほかと合わない、`legend` の読み替え先のブロックがない → 不具合(読み込みで落ちるか、遊べない面になる)
- `title` の `ja` / `en` の片方がない
- 未完成のステージを入れた → ユーザーに見えない状態か(`release-flow.md` 第1章「未完成の機能」)

### 2.4 広告(`app/lib/services/ads.dart`・呼び出し側)

審査とアカウントの停止に直結する。

- デバッグビルドで本番の広告ユニット ID を使う、テスト用 ID がリリースに入る → 不具合(AdMob の規約違反 / 収益が出ない)
- `AdsConfig` の本番 ID、`Info.plist` の `GADApplicationIdentifier`、`AndroidManifest.xml` の `APPLICATION_ID` を、理由なく変えた
- `InterstitialPolicy`(結果画面を3回見るまでは出さない・3分あける・1日8回まで)を通さずに広告を出す、プレイ中(ウェーブの途中・ボス戦)に出す → 不具合
- iOS でトラッキング許可(ATT)のダイアログより先に広告を読み込む、同意(UMP)の処理を飛ばす → 審査で落ちる
- 広告の読み込み・表示の失敗で画面遷移が止まる(`await` したまま戻らない、例外が漏れる) → 不具合(結果画面からタイトルに戻れなくなる)

### 2.5 UI・文言(`app/lib/ui/`・`app/lib/game/`・`app/lib/l10n/`)

- `app_ja.arb` と `app_en.arb` の片方にしかキーがない、プレースホルダーが食い違う → 不具合
- 画面に日本語・英語を直書きしている → `.arb` に置く
- 横画面固定。英語の長い文言や小さい端末(iPhone SE 相当)で溢れそうなレイアウト → 指摘する(確信がなければ「確かめてほしい」と書く)

### 2.6 ランキング・ネイティブ設定

- `leaderboard.dart` のリーダーボード ID、バンドル ID / applicationId、署名の設定を変えた → 意図した変更か。ストア側の設定と合わないと送信できない
- 権限(`Info.plist` の説明文、`AndroidManifest.xml` の `uses-permission`)を足した → 使う理由があるか。不要な権限は審査で落ちる。ストアのプライバシーの回答(`docs/app-store.md` / `docs/play-store.md`)の更新が要るか

### 2.7 テスト

足りなければ指摘する。ただし描画の見た目や、テストの書きにくい UI の細部までは求めない。

| 変更 | 求めるテスト |
| --- | --- |
| コアの判定・スコア・崩落・ボスの挙動 | `app/test/core/` の単体テスト。境界値(ちょうど / 1 つ手前)を含む |
| 新しいブロック・ボスの攻撃・クリア条件・星の条件 | 少なくとも 1 つ、それが働くことのテスト |
| 保存データの形式 | 古い JSON を読めるテスト |
| 広告の頻度の制限 | `app/test/services/ads_test.dart` に、時刻を差し替えたテスト |
| 不具合の修正 | 直す前に落ちるテスト(回帰テスト) |

### 2.8 Issue から作った PR(作者が `claude[bot]`、ブランチが `claude/issue-*`)

`implement-issue` スキルで作った PR。人は本文の「完了条件」「エミュレーターで確かめたこと」を見て Approve するので、それが正しいかを確かめる。

- `Closes #<番号>` の Issue を `gh issue view <番号> --comments` で読み、完了条件のうち、差分で満たしていないものに `[x]` が付いている → 不具合
- Issue の範囲を超えた変更(頼まれていない機能・整理)が入っている → 提案(大きければ不具合)
- 「確かめられなかったこと」が空なのに、音・広告・ランキング・iOS だけの処理を変えている → 提案(人が実機で確かめる項目を足すよう書く)

### 2.9 ドキュメントとの食い違い

`design.md` と `docs/native-app-spec.md` は **実装を正とする**。食い違いそのものは止める理由にしない。

- 仕様と違う挙動が、明らかに意図しない不具合に見える → 指摘する
- 仕様に書いてある値・手順を変えたのに、ドキュメントを直していない → 直すよう提案する(`needs-fix` にはしない)

### 2.10 `main` 向けの PR(リリース PR・ホットフィックス)

`baseRefName` が `main` のときだけ見る。マージは人がするので、ここでは人が確認しやすい指摘をする。

- `app/pubspec.yaml` の `version` が `release-flow.md` 第1章「バージョン名の上げ方」に合っているか(前回のタグ `git tag --list 'v*' --sort=-v:refname | head -n1` からの変更で判断する)。タグと同じバージョンのままなら、`release.yml` が何もしないので不具合
- 「新機能」の文面の 4 ファイル(`release-flow.md` 第5章)がすべて更新され、上限に収まっているか。字数は推測せず数える: `wc -m <ファイル>`(Android は **500字**、iOS は 4000字)
- 文面が今回の変更と合っているか、ユーザーに見えない内部の変更を書いていないか、日本語と英語で内容が揃っているか
- `release/*` の PR に、リリースに関係ない機能の変更が混ざっていないか

### 2.11 CI(`.github/workflows/`)

- `permissions` を広げた、シークレットをログに出しうる(`echo`、`set -x`)、フォークの PR でシークレットを使う → 不具合
- マージの条件(`.github/scripts/merge-if-approved.sh` の Approve・ジョブの結果・`needs-fix` / `hold`・`--match-head-commit`、`pr.yml` / `merge.yml` の `if`)を緩めた → 意図した変更か必ず確かめる
- `implement.yml`・`pr.yml` の `fix` の Claude に許すツール(`--allowedTools`)を広げた、`fix` の自動修正の回数の上限(`MAX_FIXES`)を上げた・数え方を変えた → 意図した変更か必ず確かめる

## 3. 重さを決める

指摘ごとに、次のどちらかを決める。

| 重さ | 基準 | 書き方 |
| --- | --- | --- |
| **直すべき**(`needs-fix`) | 遊べない・落ちる・判定や点数が間違う、保存データが壊れる・消える、審査や規約で落ちる、シークレットが漏れる、上の表のテストが欠けている | 本文の先頭に `**[要修正]**` |
| 提案 | 直したほうがよいが、出しても困らない(ドキュメントの更新、読みにくさで不具合を招きそうな箇所) | 本文の先頭に `**[提案]**` |

- 命名・書き方の好み・整形(`dart format`)・コメントの量は **指摘しない**。
- 確信がないものは、何を確かめればよいかを書いて「提案」にする。推測で `needs-fix` にしない。
- 同じ問題が何か所にもあるときは、最初の 1 か所にまとめて書く。

## 4. 結果を返す

### CI(`pr.yml`)から呼ばれたとき

`mcp__github_inline_comment__create_inline_comment` が使えるときは CI とみなす。

1. 指摘は、該当行へのインラインコメントで日本語で書く。何が起きるか(例: 「ステージ 1-7 の記録が読めなくなる」)と、直し方を書く。
2. 最後に `gh pr comment <番号> --body '...'` で全体の所見を短くまとめる。`[要修正]` の数、`[提案]` の数、見た観点(2.x のどれを見たか)を書く。問題がなければ「問題なし」とだけ書いてよい。
3. ラベルを付け外しする。
   - `[要修正]` が 1 つでもある: `gh pr edit <番号> --add-label needs-fix`
   - ない: `gh pr edit <番号> --remove-label needs-fix`(付いていなくてもそのまま実行してよい)

コードは直さない。push もしない。`needs-fix` を付けると、`pr.yml` の `fix` ジョブが `[要修正]` の指摘を 1 つずつ確かめ、妥当なものを直す(`.claude/skills/pr-fix/SKILL.md`)。そのため `[要修正]` の指摘には、どのファイルの何行で何が起きるかを、確かめられる形で書く。

### 手元(Claude Code)で呼ばれたとき

指摘を `ファイル:行` 付きで会話に返す。PR へのコメントとラベルの付け外しは、ユーザーに頼まれたときだけする。
