# レビューの指摘の確かめと修正

`pr.yml` の `review`(`.claude/skills/pr-review/SKILL.md`)が `needs-fix` を付けると、`fix` ジョブがこの手順を動かす。直したコミットはワークフローが push し、`pr.yml` がもう一度動く。再レビューで `[要修正]` がなくなれば `needs-fix` が外れ、人が Approve するとマージされる(`docs/release-flow.md` 第1章)。

レビューも間違える。**指摘を鵜呑みにして直さない。** 妥当でない指摘を直すと、動いていたものを壊したうえに、人は「レビューで直った」と思って Approve する。逆に、妥当な指摘を「妥当でない」と退けると、`needs-fix` が付いたまま人の判断に回る(マージはされない)ので、迷ったら退けるほうに倒す。

**自分でしないこと**: push(ワークフローがする)、ラベルの付け外し、PR のマージ・Approve、`[提案]` の指摘の修正、指摘されていない箇所の変更・整理・整形、`.github/` の変更(Claude の GitHub アプリはワークフローのファイルを push できない。`.github/` への指摘は「人に任せる」にする)。

## 1. 指摘と変更を集める

```sh
cat "$FINDINGS"                      # CI では、この実行のレビューの [要修正] の一覧(JSON)。id・path・line・body・url
gh pr view <番号> --json number,title,body,baseRefName,headRefName,files
gh pr diff <番号>
```

- 手元で `FINDINGS` がないときは、`gh api --paginate repos/{owner}/{repo}/pulls/<番号>/comments` から、`claude[bot]` が書いた、返信でない、本文が `**[要修正]**` で始まるものを拾う。
- `pr-review` スキルを読み、その指摘がどの観点(2.x)のものかを把握する。
- Issue から作った PR(`Closes #<番号>`)なら、`gh issue view <番号> --comments` で完了条件も読む。

## 2. 指摘を 1 つずつ確かめる

指摘ごとに、次の 3 つのどれかに決める。

| 判定 | 基準 | すること |
| --- | --- | --- |
| **妥当** | 指摘の言う問題が、実際の呼び出し元・入力から起きることを、コードを追って示せる(テストで再現できればなおよい) | 3 で直す |
| **妥当でない** | 指摘の前提がコードと違う(すでに処理されている・その経路では起きない・別の箇所で守られている)、または `pr-review` の基準では `[要修正]` に当たらない(好み・整形・ドキュメントだけの話) | 直さない。理由を返す |
| **人に任せる** | 直し方が仕様や遊び心地の判断を要する、保存データの互換・広告・ストアの設定に関わる直し方が複数ある、Issue の範囲を超える、`.github/` の変更が要る | 直さない。何を決めてほしいかを返す |

確かめ方:

- 差分だけでなく、チェックアウトしたファイルで、変更した関数の呼び出し元・テスト・関連する JSON を読む。
- コアの判定・スコア・保存データの読み書きの指摘は、**直す前に、指摘どおりなら落ちるテストを書いて** `flutter test <ファイル>` で動かす。落ちれば妥当。通れば、指摘の前提を読み直す(テストが指摘の状況を作れていないこともある)。
- テストが「足りない」という指摘(`pr-review` 2.7 の表)は、表の変更に当たるか、既存のテストがすでに覆っていないかを確かめる。当たって覆っていなければ妥当。
- 「確かめてほしい」と書かれた指摘(レビューが確信を持てなかったもの)は、確かめられたときだけ妥当にする。

## 3. 妥当な指摘を直す

- 指摘の問題を直すのに要る最小の変更にする。ついでの整理・整形はしない。
- 2 で書いた落ちるテストは残す(回帰テストになる)。テストが足りないという指摘なら、`pr-review` 2.7 の表のテストを足す。
- `pr-review` の観点(コアの決定性、Tuning、`GameEvent`、`.arb` の両方、保存データのキー)を、直した箇所でも守る。直したことで新しい `[要修正]` を作らない。

```sh
cd app
flutter analyze
flutter test
```

両方が通るまで直す。通せなければ、その指摘の変更を戻して「人に任せる」にする(`git checkout -- <ファイル>`)。ワークフローも push の前に同じチェックを動かし、通らなければ push しない。

## 4. コミットする

妥当な指摘を 1 つでも直したら、**コミットを 1 つ** 作る。最後の行の `Review-Fix: auto` は、ワークフローが自動修正の回数を数えるのに使うので変えない。

```sh
git add <直したファイル>
git commit -m "レビューの指摘を直す: <何を直したか>" -m "<指摘ごとに 1 行>" -m "Review-Fix: auto"
git rev-parse --short HEAD   # 返信に書く
```

直したものがなければコミットしない。

## 5. 結果を返す

### CI(`pr.yml` の `fix`)から呼ばれたとき

1. 指摘ごとに、そのスレッドへ返信する。

   ```sh
   gh api -X POST repos/<REPO>/pulls/<番号>/comments/<指摘の id>/replies -f body='...'
   ```

   - 妥当: `**[修正]** <直したこと>。コミット <短い SHA>(このあとワークフローが push する。テストが通らなければ push せず、その旨をコメントする)`
   - 妥当でない: `**[妥当でないと判断]** <理由。どのファイルの何行で守られているか、どの経路では起きないか>`
   - 人に任せる: `**[人の判断が要る]** <何を決めてほしいか、選択肢>`

2. 最後に `gh pr comment <番号> --body '...'` で、直した数・妥当でないと判断した数・人に任せた数をまとめる。直していない指摘が残るときは「`needs-fix` は付いたままなので、返信を読んで判断してほしい(妥当でないと思えばラベルを外して Approve、直すなら `@claude` で頼む)」と書く。

### 手元(Claude Code)で呼ばれたとき

指摘ごとの判定と理由を会話に返す。コミットまではしてよいが、push・PR へのコメントはユーザーに頼まれたときだけする。
